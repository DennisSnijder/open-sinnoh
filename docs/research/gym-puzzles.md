## Shared lifecycle, timing and collision rules

`PersistedMapFeatures` is one tagged save slot (`id` plus a 32-byte `buffer`), embedded in `MiscSaveBlock`, not seven independent permanent puzzle records. `InitWithID` clears the entire slot before setting its tag. Runtime props, animation handles, collision caches and task phases are separate from that saved payload. Dynamic init/free/collision dispatch follows the tag; Hearthome has no dynamic collision callback and Snowpoint is not a member of this dispatch at all. Sources: [persisted structure](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/include/persisted_map_features.h#L6-L16), [misc save](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/include/savedata_misc.h#L20-L37), [clear/select/access](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/src/persisted_map_features.c#L5-L27), [dispatch](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/src/dynamic_map_features.c#L20-L103).

A normal warp calls `FieldMapChange_UpdateGameData(..., FALSE)`: it clears local flags, clears the persisted slot, selects the new camera and runs `INIT_SCRIPT_ON_TRANSITION`. Map construction separately runs on-load/on-resume and rebuilds dynamic features. A reload or return from a battle must rebuild runtime presentation from saved state without replaying transition initialization. The gym-specific sections explain which other saved vars or objects restore progress; a cleared feature slot alone does **not** imply all progress is lost. Sources: [warp update](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/src/field_map_change.c#L248-L302), [ordinary transition call](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/src/field_map_change.c#L447-L481), [map construction](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/src/overlay005/fieldmap.c#L165-L225), [dynamic reconstruction](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/src/overlay005/fieldmap.c#L870-L899).

Save-backed map objects matter independently of the feature buffer: the field saves/restores up to 64 objects, including status, identity, graphics, movement type, data slots, coordinates and height. Veilstone and Snowpoint use this to retain puzzle changes across a save or battle rebuild. Save only at a settled state in our engine (the existing save contract rejects active scripts/world tasks); do not invent a serialization format for half-played native animation tasks. Sources: [field object save/load](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/src/field_overworld_state.c#L143-L153), [object serialization](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/src/map_object.c#L424-L546); engine seam: `packages/contracts/src/field.ts`, `packages/contracts/src/state.ts`, `docs/contracts.md`.

One main-loop frame here means **one 30 Hz simulation tick**. `NitroMain` runs the application and main task manager once, with two vblank waits in the normal loop; do not halve these durations. Animation-clip completion remains clip-dependent; a source task's movement duration excludes input, dialogue, fades and its setup/cleanup states unless explicitly included. Native `ScrCmd` returning `FALSE` continues the command loop; `TRUE` yields, and a called field task or installed pause determines the actual wait. Sources: [main loop](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/src/main.c#L119-L162), [script executor](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/src/field_script_context.c#L58-L101).

**Player collision and trainer sight are different queries.** The player query first resolves vertical direction, then asks the dynamic feature for a collision override; without an override it uses static attributes and dynamic-height behavior. Ordinary trainer sight checks facing/range, undefeated status and every tile of its approach path via `sub_02063E94`, whose map-object query uses `TerrainCollisionManager_WillMapObjectCollide`, bypassing the player's dynamic-feature mask. Thus one cannot infer that every moving bag, water mask or gear blocks a trainer's sight. Dynamic height, static terrain and object occupancy can still affect that path. Hearthome additionally has explicit light/sight logic. Sources: [player versus object collision](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/src/terrain_collision_manager.c#L279-L337), [sight selection](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/src/trainer_encounter.c#L132-L255), [sight obstruction](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/src/trainer_encounter.c#L310-L347), [map-object path query](https://github.com/pret/pokeplatinum/blob/1dc13dcea40c04ab53f1f607de46023dc409ef20/src/map_object_move.c#L576-L614).

## Eterna: the flower clock

**Maps and durable state.** Platinum uses `MAP_HEADER_ETERNA_CITY_GYM` (67; the generated header list is zero based), area `026`, matrix `220`, matching gym scripts/events, interior orthographic camera, no running or bicycle. Do not use the adjacent Diamond/Pearl gym header. The feature is `EternaGymClockPersistedFeature.state` (`u32`), with initial/three trainer/leader states 0–4. `InitPersistedMapFeaturesForEternaGym` (0x2C9) has no arguments, clears/selects the shared feature buffer and returns FALSE immediately. Crucially, dynamic-map construction then overwrites that zero from `VAR_ETERNA_GYM_FLOWER_CLOCK_STATE`: the saved system variable, rather than the transient zero, governs re-entry. `AdvanceEternaGymClock` (0x2CA), also argument-free, increments both copies before starting its task; at 4 it starts nothing and does not increment. Its handler still returns TRUE. **Lifecycle and implementation proposal.** Leaving or blacking out discards runtime props/task storage, but the flower-clock system variable and won-trainer progression survive; re-entry's transition init selects/zeros the feature, then dynamic construction reconstructs hands/fountains from that variable. A normal save at rest serializes the shared feature and system vars; reload reconstructs the final stage. There is no supported menu/save/exit opportunity during a field task or battle; an engine-internal snapshot during rotation is a separate capability, not evidenced native behavior. Proposed importer records: hand model references, authored clock/jump/collision data and fountain effect references (read from the user's import, never checked-in copied tables). `FieldHost`: init/advance plus completion and message-input integration, state-aware collision/jump and camera tracking. `FieldView`: two rotations, fountain visibility/drain phase and camera target. `GameState`: clock phase and existing flower-clock/trainer vars; keep transient camera/animation task progress separate. ## Hearthome: dark rooms, clues and doors

**Maps and saved state.** Platinum's entrance/trainer-room-1/trainer-room-2/leader-room headers are 88/89/90/91, area `027`, matrices `222`–`225`, with default camera and no running/bicycle; the subsequent `DP_GYM_*` maps and `MoveHearthomeGymDPLift` are legacy mechanisms, not this puzzle. `HearthomeGymPersistedFeatures` has four signed 16-bit fields: `initialized`, `correctDoorID`, `clueX`, `clueZ`. `InitPersistedMapFeaturesForHearthomeGym` (0x171), no operands, returns FALSE immediately; its common initializer clears the whole shared buffer before selecting Hearthome. Both trainer rooms call it on transition, after setting map-local var 0 to zero. There is no Platinum update/press script opcode: map construction randomizes and patches doors; field control handles transitions and sight each frame. **Track mechanics.** Bags use a separate 32×32 authored track grid, not an ordinary terrain tile-behaviour enum. Its semantic values are open track, prohibited destination, prohibit north/south (unused), prohibit east/west, stop point, and prohibit west. Evaluate direction restrictions and stop points at the **current** cell, and a wall or stack at the **next** cell. An initial stop point alone permits another shove; a stack already adjacent gives zero travel and does not topple. Otherwise advance until a nonzero condition: stop on the current cell before a wall/stack, or on a stop point. The algorithm does not test other bags as track obstacles. At completion it snaps the collision object's X/Z to the visual endpoint; the intermediate renderer movement does not move that object's logical X/Z every frame. If a stack is immediately beyond that endpoint, animate then delete the stack's object and renderer, opening its collision tile. The gym's dedicated collision callback returns FALSE, so ordinary object/terrain collision remains responsible for blocking the player. Rendering initially recalculates floor height and offsets the models upward by six world units. ## Integration and replay acceptance

The field code owns puzzle simulation, imported geometry and presentation; the script command handlers resolve operands, call `FieldHost`, and poll completion. Add a tagged active feature state and saved dynamic-object identities, not a permanent solved-layout registry: the native reset rules above differ by gym. Keep source integer/fixed-point rounding where it affects movement endpoints, collision or task milestones. `FieldView` is a read-only projection of that world state; rendering interpolation must never advance the simulation. ## Sunyshore table location verified during implementation (2026-10-16)

US rev0 overlay 8 loads at `0x02249960`. The separate pin is `0x2D78–0x4E1C`: gear-array pointers at `0x2DE0`, rectangle-array pointers at `0x2DEC`, and three 20-byte collision-selection records at `0x4DE0` (count plus four pointers). Gear payloads are eight-byte records; rectangle payloads four bytes. Both the early lists and final pointer records fall outside the former `0x2E04–0x4DDC` pin. `packages/importer/src/gyms/sunyshore.ts` follows and bounds-checks these pointers. Original writer tests place payloads at different offsets to prove the decoder follows pointers. ROM-derived payloads remain local.
